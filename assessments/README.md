# Assessments

This directory contains diagnostic exams, sprint checks, comprehensive assessments and their results.

Assessments are used to measure actual skill development over time.

The purpose is not to collect grades.

The purpose is to answer:

- what I can explain without help;
- what I can implement independently;
- what I can troubleshoot;
- what knowledge has survived after time has passed;
- which skills require another learning cycle.

## Structure

### `baseline-2026-08/`

Contains the original Assessment Week materials that established Baseline v1.0.

This may include:

- exam documents;
- completed answer sheets;
- assessment trackers;
- review spreadsheets;
- summaries and supporting artifacts.

These files represent the original starting point and should generally not be modified after being archived.

### `sprint-checks/`

Contains assessments performed at the end of individual learning sprints.

A sprint check may include:

- short theory questions;
- hands-on tasks;
- troubleshooting;
- code or configuration review;
- a small engineering case.

Sprint checks are narrower than comprehensive assessments and focus primarily on the current sprint while still reusing previous skills.

### `comprehensive/`

Contains larger cumulative assessments.

These assessments combine multiple areas and are intended to test whether previously learned skills can be used together.

Examples:

- CS + Python + Git + Linux;
- Linux + networking + services + automation;
- API + SQL + Docker + Nginx;
- infrastructure + security + troubleshooting.

## Assessment principles

Assessments should measure independent capability.

Unless explicitly stated otherwise:

- no AI assistance;
- no answer keys;
- no copying ready-made solutions;
- documentation availability is defined separately for each assessment;
- uncertainty should be recorded honestly;
- unknown answers may be left as `не знаю` rather than guessed.

## Raw artifacts

Original completed assessment files should be preserved.

If an assessment is reviewed later, corrections should not silently replace the original answers.

Instead, keep:

1. the original submission;
2. the review;
3. later recheck results.

This preserves an honest history of progress.

## Naming convention

Recommended naming examples:

`exam-01-computer-science.docx`

`exam-01-computer-science-completed.docx`

`assessment-week-tracker.xlsx`

`sprint-01-check.docx`

`sprint-01-review.md`

`comprehensive-control-01.docx`

Exact names may vary, but they should remain understandable without opening the file.

## Relationship with Baseline

Assessment artifacts are the evidence.

The documents in `docs/baseline/` are the interpretation of that evidence.

In other words:

`assessment → review → skill update → baseline/roadmap decision`
